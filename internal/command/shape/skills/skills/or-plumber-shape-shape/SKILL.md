# Shape — `plumber:shape`

`plumber:shape` is the entry-point annotation for **template-driven
generation**. It hands the annotated node (struct or interface) to one
or more named Go `text/template`s, and writes the rendered output to a
file. Unlike `plumber:derive`, which mechanically projects a subset of
fields, `plumber:shape` is fully programmable through templates and
`plumber:scope` injections.

This skill is the deep-dive for `plumber:shape`. For a high-level
overview of the `shape` command see the `or-plumber-shape` skill. The
catalog of registered modifier annotations and their YAML schemas lives
in `or-plumber-shape-annotations`. The catalog of template helper
functions lives in `or-plumber-shape-functions`.

## When to use

- Rendering boilerplate from a custom Go template (e.g. converters,
  registries, gRPC stubs).
- Generating code that depends on **interface methods** — `plumber:shape`
  accepts both structs and interfaces; `plumber:derive` does not.
- Producing multiple outputs from one source type by pointing the
  annotation at several templates.
- Generating code for a model declared elsewhere — pair `plumber:shape`
  with `plumber:context` in any free-floating comment group.

## Minimal example

```go
// plumber:shape Converter
// plumber:template converter
// plumber:output {{ filename_suffixed "converter" }}
type OrderModel struct {
    ID   string
    Name string
}
```

With a configured template `converter`:

```yaml
plumber.shape:
  templates:
    content:
      - name: converter
        content: |
          // Code generated by plumber. DO NOT EDIT outside plumber::Block.
          package {{ .Package.Name }}

          func {{ .Name }}From(src {{ .Type.Name }}) {{ .Name }} {
              return {{ .Name }}{
              {{- range .Type.Fields }}
                  {{ .Name }}: src.{{ .Name }},
              {{- end }}
              }
          }
```

## Templates

Pick the template(s) with `plumber:template <name>`. The annotation may
be **repeated** to apply several templates to the same node — each
produces its own rendered chunk concatenated into the output.

Templates are resolved in priority order:

1. Inline content under `plumber.shape.templates.content`.
2. `plumber.shape.sources` entries (local directories or git
   repositories).
3. Root-level `plumber.templates` (shared with discovery, etc.).

The catalog of helpers available inside a template (Sprig, plumber
generic, render-stage helpers like `module`, `annotation`,
`path_join`) is described in `or-plumber-shape-functions`.

## Built-in command templates

The shape renderer ships a fragmented scaffold under the
`plumber/command/shape/...` namespace, split across three files. The
top-level dispatcher routes to either the **struct** branch or the
**interface** branch based on the subject's kind. The default block
bodies are intentionally minimal (some are empty stubs) so individual
blocks can be redefined without replacing the surrounding structure.

To customise output:

1. Author a template body that uses
   `{{ define "plumber/command/shape/..." }}` to override one or more
   blocks.
2. Register it in `plumber.shape.yaml` under
   `plumber.shape.templates.content` (or expose it via
   `plumber.shape.sources`) — give it a **registered name**.
3. Reference the registered name from source comments with
   `plumber:template <registered-name>`. The annotation may be repeated;
   `define` blocks across all referenced templates are merged into the
   render. Blocks not redefined fall back to the defaults below.

`plumber:template` takes the **registered template name**, never a
built-in block name. The block names below are an internal contract for
`{{ define }}`/`{{ template }}` only.

### `command_shape.gtpl` — dispatcher

| Block | Default behaviour | Override use |
|---|---|---|
| `plumber/command/shape` | Resolves `plumber:name` and dispatches to `…/shape/interface` or `…/shape/struct` based on subject kind. | Replace the entire shape scaffold (rare). |
| `plumber/command/shape/comment/shaped` | Emits `// <Name> is shaped from <FQN>.`. Used by the interface branch as a header. | Customise the generated-type header comment. |

### `command_shape_struct.gtpl` — struct branch

| Block | Default behaviour | Override use |
|---|---|---|
| `plumber/command/shape/struct` | A single line: `// to be overridden by the user's template`. | **Primary override target** for struct-shaped types — the user-registered template provides the actual struct body. |

> **Caveat.** A `plumber:shape` on a struct **without a registered
> template that defines `plumber/command/shape/struct`** produces
> effectively empty output (just the placeholder comment). Always
> register at least one template when shaping struct types.

### `command_shape_interface.gtpl` — interface branch

The interface branch generates a forwarding wrapper struct, a
`New<Name>` constructor, and per-method stubs inside a
`fragment_start "struct" / fragment_end` pair.

| Block | Default behaviour | Override use |
|---|---|---|
| `plumber/command/shape/interface` | Top-level: emits the header comment, `type <Name> struct { … }`, `New<Name>(…)` constructor, and the methods loop. | Replace the entire interface scaffold (rare). |
| `plumber/command/shape/interface/struct` | Empty (struct body of the wrapper). | Add fields the wrapper holds (delegate, logger, metrics, …). |
| `plumber/command/shape/interface/initializer/params` | Empty. | Constructor parameter list. |
| `plumber/command/shape/interface/initializer/body` | Empty. | Constructor field assignments. |
| `plumber/command/shape/interface/methods` | Iterates `.Type.Interface.Methods`, skips non-definable ones, renders each via `…/interface/method`. | Restrict, group, or reorder forwarded methods. |
| `plumber/command/shape/interface/methods/extra` | Empty. | Add extra methods outside the main loop (e.g. unexported helpers). |
| `plumber/command/shape/interface/method` | Emits `func (<recv> *<Name>) <Method>(<params>) (<results>) { <body> }`. | Replace the per-method scaffolding wholesale. |
| `plumber/command/shape/interface/method/comment` | Empty. | Per-method doc comment. |
| `plumber/command/shape/interface/method/params` | Renders `<name> <type>,` per arg. | Customise param rendering (e.g. drop `ctx`). |
| `plumber/command/shape/interface/method/results` | Renders `<name> <type>,` per result. | Customise result rendering. |
| `plumber/command/shape/interface/method/body` | Single statement: `return`. | Insert real forwarding (e.g. via `…/method/forward`), tracing, error wrapping. |
| `plumber/command/shape/interface/method/forward` | Helper — emits `<results> = <Ident>.<Method>(<args>)`. Not invoked by default. | Call from a custom `…/method/body` to build a forwarder. Caller must `extend` the scope with `Ident`. |
| `plumber/command/shape/interface/method/call/arguments` | Renders comma-separated arg/result names (used by `…/method/forward`). | Helper; rarely overridden. |

### Scope variables

Variables exposed to the blocks above:

| Variable | Available in | Description |
|---|---|---|
| `$.Type` | All blocks | The annotated source type. `.Type.Interface` / `.Type.Struct` selects the dispatch branch. `.Type.Interface.Methods` drives the methods loop. `.Type.Spec.FQN`, `.Type.Name`. |
| `$.Scope.Subject` | All blocks | The annotated node carrying the `plumber:shape` block (used by `annotation_value`, `comment`, `receiver`). |
| `$.Scope.Name` | All blocks under `…/shape` | Resolved generated-type name (from `plumber:name` or default). |
| `$.Scope.Receiver` | Interface method blocks | Receiver identifier (e.g. `r`) — produced by `receiver $.Scope.Subject`. |
| `$.Scope.Method` | Interface method blocks | Current `*model.Method` — `.Args`, `.Results`, `.Name`. |
| `$.Scope.Ident` | `…/method/forward` | Identifier the forwarder calls into. The caller must supply it via `extend . "Ident" "..."` before invoking the helper. |

### Worked example — interface forwarder

Two registered templates, merged at render time. The first adds a
delegate field plus constructor wiring; the second supplies the method
body that forwards through the delegate using the built-in
`…/method/forward` helper.

```yaml
plumber.shape:
  templates:
    content:
      - name: forwarder.struct
        content: |
          {{ define "plumber/command/shape/interface/struct" -}}
              delegate {{ .Type.Spec.FQN | type }}
          {{- end }}
          {{ define "plumber/command/shape/interface/initializer/params" -}}
              delegate {{ .Type.Spec.FQN | type }},
          {{- end }}
          {{ define "plumber/command/shape/interface/initializer/body" -}}
              delegate: delegate,
          {{- end }}
      - name: forwarder.body
        content: |
          {{ define "plumber/command/shape/interface/method/body" -}}
              {{ template "plumber/command/shape/interface/method/forward"
                 (extend . "Ident" (printf "%s.delegate" .Scope.Receiver)) }}
          {{- end }}
```

Reference both registered names from the source type:

```go
// plumber:shape WorkerForwarder
// plumber:template forwarder.struct
// plumber:template forwarder.body
type Worker interface { ... }
```

The scaffold (struct declaration, constructor, methods loop, method
signature) is preserved — only the holes are overridden.

For the catalog of helpers callable inside these blocks (`type`,
`coalesce`, `receiver`, `type_method_definable`, `type_set`,
`fragment_start`, `fragment_end`, `comment`, `extend`, …) see
`or-plumber-shape-functions`. For the matching scaffold on the
`plumber:derive` side see `or-plumber-shape-derive`.

## Modes

`plumber:shape` honours `plumber:mode`:

| Mode | Behaviour |
|---|---|
| `generated` (default) | Writes a new file with a `// Generated file...` header. Lines outside `plumber::Block(...)` fences are overwritten on each run. |
| `inplace` | Idempotently merges declarations rendered by the template into an existing file. Adds missing types, methods, vars; preserves existing ones. See the `or-plumber-shape-derive` skill for the full merge semantics — they apply identically here. |

## Scopes

`plumber:scope` injects additional resolved values into the template
under `.Scope.Custom.<Name>`. The annotation may be repeated.

| Form | Effect |
|---|---|
| `plumber:scope "Repo" type='"pkg/path".Repo'` | Resolve a Go type and inject it; templates can call `.Scope.Custom.Repo.Methods` etc. |
| `plumber:scope "Mode" value="strict"` | Inject a plain string. |

`type` and `value` are mutually exclusive. Use scopes to feed templates
data the source type alone does not carry — sibling types, fixed
strings, or a target type for converter generation.

## Filters and wrappers

Templates iterate `.Type.Fields` / `.Type.Methods` directly. Filters and
field wrappers from `plumber:filter` / `plumber:field_wrapper` apply to
this iteration the same way they do for `plumber:derive`. See
`or-plumber-shape-derive` for the field-filter mechanics.

## Output filename templates

`plumber:output` is rendered as a Go `text/template` and exposes
`.Filename`, `.Name`, `.Ext`, plus the `filename_suffixed` helper. See
the `or-plumber-shape-derive` skill for the table of expansions —
`plumber:shape` uses the same renderer.

Always use `{{ filename_suffixed "..." }}` (or another distinct path)
for `generated` mode. Otherwise the source file is overwritten on the
next shape run.

## Notifications

Pair `plumber:shape` with `plumber:notify <handler> [k=v ...]` to run a
post-generation tool when the shape run completes (e.g. `goverter`,
`protoc`, `stringer`):

```go
// plumber:shape Converter
// plumber:template converter
// plumber:notify goverter path="internal/converters"
type Order struct { ... }
```

Handler commands are configured under `plumber.shape.handlers`. Named
arguments are aggregated across all `plumber:notify` annotations
targeting the same handler. See `or-plumber-shape` for the handler
configuration format.

## Declaring shape transformations from a detached comment group

Like `plumber:derive`, a `plumber:shape` block can be declared from
**any free-floating comment group** in the package — the package
doc-comment, a block between two declarations, or any comment group not
attached to a declaration — by pairing it with `plumber:context`:

```go
package contract

// plumber:context "github.com/example/contract".Worker
// plumber:shape WorkerStub
// plumber:template worker_stub
// plumber:output {{ filename_suffixed "stub" }}

// NewWorker constructs a Worker.
func NewWorker(...) *Worker { ... }
```

The block must be a **free-floating** comment group — keep a blank line
above or below so Go's parser does not attach it to a neighbouring
declaration.

`plumber:context` supports two forms:

- `plumber:context "pkg/path".Type` — single-type targeting.
- `plumber:context pkg/path matcher=<name>` — package + matcher mode,
  applying the bundle to every type in the package matched by the named
  matcher.

This is the recommended way to keep a model's own doc-comment free of
codegen annotations, or to drive shape transformations on third-party
types you cannot edit. The schema of `plumber:context` is documented
under `or-plumber-shape-annotations`.

## Single-type mode

Bypass annotation scanning entirely with `shape target`:

```bash
plumber shape target \
  --config plumber.shape.yaml \
  --type Order \
  --macro '@shape' \
  --macro-named-arg template=converter
```

The macro `@shape` must be configured in `plumber.shape.macros` — see
`or-plumber-shape-annotations` for the registered macros in this project.

## Key rules for agents

- **`plumber:shape` works on structs and interfaces.** For interface
  methods or fully programmable rendering, prefer it over
  `plumber:derive`.
- **`plumber:template` may be repeated.** All listed templates render
  into the same output file in declared order.
- **Templates must be declared in config** (inline content, local source,
  or git source) — references that resolve nowhere fail the run.
- **Use `plumber:scope` to enrich the template context** with sibling
  types or constant values; don't bake import paths into the template.
- **`plumber::Block(...)` fences mark hand-written islands** in
  generated files. Everything outside is regenerated on each run.
- **`{{ filename_suffixed "..." }}` for output filenames** prevents
  overwriting the source file in `generated` mode.
- **Use `plumber:context` in a free-floating comment group** to drive
  shape transformations without editing the source type's doc-comment.
- **Discover available templates, scopes, and helpers** via
  `or-plumber-shape-annotations` (registered options) and
  `or-plumber-shape-functions` (template helpers).
- **`plumber:template` takes a registered template name**, not a
  built-in block name. Register a template in
  `plumber.shape.templates.content` (or via a source) whose body uses
  `{{ define "plumber/command/shape/..." }}` to override scaffold
  blocks. Repeat the annotation to merge overrides from multiple
  registered templates.
- **A `plumber:shape` on a struct without an override of
  `plumber/command/shape/struct`** produces empty output — always
  register at least one template when shaping struct types.
